# Resource ownership and limits

This audit covers the Mu4 source based on `afba9f0a`, plus the async-output, rate-limit cleanup and connection-admission changes described below. It traces ordinary request, response, connection and callback lifetimes. It is a code audit with bounded correctness tests, not a capacity measurement, parser review or proof that all allocation paths are bounded. See also [HTTP/2 concurrency](HTTP2-CONCURRENCY.md).

## Main findings

Mu4 has useful per-request and per-connection limits, including opt-in server-wide connection admission, but **no server-wide memory budget**. The default 1,000 concurrent request slots do not cap idle sockets, sockets in setup, upgraded WebSockets, pending writes within a request, or application state retained by callbacks. Virtual threads reduce the cost of waiting; they do not put a limit on that work.

Two async-output allocation/retention problems are fixed here:

* A completed write future previously retained its payload, callback and response through the queued-write object. The public future now detaches from its response before publishing completion. Queued callbacks no longer capture the payload entry. Failures can still retain a supplied exception, and application callbacks can retain anything their own closures capture.
* Direct and read-only buffers previously caused a heap copy equal to the entire remaining payload. Copying now uses at most 8 KiB of scratch space per active write, with one final flush. Array-backed buffers retain their existing direct-array path. This bounds the copy, not the submitted payload or pending-write queue.

## Inventory

Defaults below are configuration defaults, not measured heap or process-memory costs. Higher application settings can raise the corresponding bounds.

| Resource and owner | Bound / backpressure | Retirement and caveats |
| --- | --- | --- |
| Accepted/setup and established sockets — `ConnectionAdmission`, `ConnectionAcceptor` | `withMaxConnections(n)` caps admitted connections across HTTP and HTTPS, from setup through idle/active HTTP, H2 and WebSockets. Default zero is unlimited. Full listeners pause acceptance; `withListenBacklog(n)` requests an OS listen backlog per port (default 50; the platform may cap or ignore it). Default idle timeout is 10 minutes. | Failure, timeout and shutdown close/retire tracked sockets and release admission idempotently. Idle listeners do not reserve slots; simultaneous accepts may race, with an excess socket closed before setup and counted as overload rejection. The cap excludes the OS backlog and transient rejected candidates. TLS/socket/kernel buffers add costs outside these Java collections. |
| Active HTTP requests — `RequestAdmission`, `Mu3ServerImpl` | Default 1,000 slots, with overload rejection. | Request completion releases the slot; upgrade releases it while the WebSocket remains live. Slots do not represent a byte reservation. |
| Execution — `ExecutionResources`, `MuServerBuilder` | Default virtual thread per task on Java 21+ in AUTO; cached platform pool otherwise. Neither puts a hard cap on submitted internal work. A supplied application executor has its own policy. | Owned internal executor shuts down before owned application executor, allowing final I/O callbacks to be submitted. Caller-owned executors remain caller-owned. Blocking application callbacks can delay application termination. Do not substitute a small internal pool without proving I/O and cleanup can progress. |
| HTTP/1 input — `Http1MessageParser`, `Mu3Request` | 8 KiB read buffer; default URL/header limits 8 KiB each; body limit 24 MiB. Streaming avoids whole-body aggregation. | Completed requests leave the pipeline; existing retention tests exercise repeated ordinary requests. `readBodyAsString()` aggregates the body and creates the result string: the wire-byte limit is not a heap-allocation limit. Multipart/parser internals are outside this audit. |
| HTTP/2 streams — `Http2StreamRegistry`, `Http2ConfigBuilder` | Default 200 concurrent streams per connection, including unfinished application exchanges after reset. Default frame size 16 KiB and header table 4 KiB. | Reset and application completion are distinct lifecycle transitions. Retained application exchanges keep their slot until the application finishes; connection-level limits multiply with connection count. |
| HTTP/2 inbound DATA — `Http2InboundFlowControl`, `Http2BodyInputStream` | Connection receive credit starts at 65,535 bytes, shared across streams; stream credit defaults to 65,535. Credit returns with consumption/discard, not just receipt. | Failure/discard clears queued body frames and returns appropriate credit. This bounds unread flow-controlled data, not exact heap: frame objects, partially consumed arrays, trailers and end markers add overhead. Empty DATA without an end marker is not retained as a body queue entry. |
| HTTP/2 outbound — `Http2Stream`, `Http2WriteCoordinator` | Blocking DATA producer splits frames and waits for each write. Coordinator mailbox and pending queue have no hard count/byte cap; flow control constrains transmission, not all queued commands. Wakeups are coalesced. | Writer failure fails in-flight and queued tasks; stream reset removes affected pending output. Connection admission/state locking prevents new writes after closure. `commandBatch.clear()` releases elements but retains its peak array capacity. Bounded streams alone do not prove a bounded control-command backlog. |
| HTTP/2 batching — `Http2WriteBatch` | 256-byte small buffer per writer; 16 KiB maximum scratch lease. Shared cache holds at most 64 idle leases: 1 MiB of array payload per classloader, plus active leases and object overhead. | Scratch returns after flush/discard releases ownership; the connection writer calls release in `finally`. This is intentionally retained reusable storage, not a global 1 MiB ceiling. |
| Response buffering and gzip — `Http1Response`, `Http2Response`, `GZIPEncoder`, `ResponsePrintWriter` | Output buffering is per response and caller-configurable. Gzip uses a configured output buffer (default 512 bytes), plus compressor state; writer encoding adds its own buffers. Streaming output does not require assembling the full response. | Response completion closes the writer/stream chain; gzip delegates native deflater cleanup to the JDK close path. Forced transport closure lets blocked output unwind. The 512-byte gzip setting is not the compressor's total memory cost. Custom encoders can allocate additional state. |
| HTTP async output — `AsyncResponseOutput` | One active write per response; pending count and bytes are uncapped. Next-write-from-callback or waiting for each future applies producer backpressure. Direct/read-only copying now uses at most 8 KiB scratch. | Failure cancels queued writes and aborts active I/O; active completion waits for I/O acknowledgement before returning buffer ownership. Completed public futures now detach. A stalled caller-owned executor may retain scheduled runners and callbacks. |
| Completion callbacks/listeners — `SerialApplicationTasks`, `ApplicationTaskContext`, `BaseResponse` | Serialized queues and application-registered listeners have no hard count cap. I/O completion is independent of callback execution. | Queues drain and consumed entries are removed; rejected serialized dispatch clears queued entries and invokes rejection handling. An indefinitely blocked callback or arbitrarily large closure can retain application state. A callback queue is not made bounded by a small executor. |
| WebSocket input — `WebsocketConnection`, `BaseWebSocket`, `SimpleWebSocket` | Default frame and full-message limit 64 KiB. Normal receive dispatch waits for the current application event to finish before reading further input. | Fragment aggregation lives until message completion/session cleanup; configured limits and transient copies affect cost. Event queue has no explicit capacity; normal receive sequencing supplies backpressure. This is not an outbound-message limit. |
| WebSocket output — `MuWebSocketSession`, `WebsocketConnection` | Blocking sends wait for the write lock/socket. Each async send submits a task; no pending count/byte cap. | Connection closure unblocks writes; completion dispatch follows the I/O result. Repeated async sends to a slow peer can retain many messages/tasks despite serialized socket output. Chain callbacks to bound production and preserve order. |
| SSE — `AsyncSsePublisher`, REST `JaxSseEventSinkImpl` | Event text/serialized bytes are assembled before async output; no separate event-size or pending-event cap. | Inherits async-output cleanup. Wait/chain completion before producing another event. A single huge event can still require a large allocation. |
| Timers — `MuServerBuilder`, connection and WebSocket maintenance | Default scheduler removes cancelled tasks and disables delayed/periodic execution after shutdown. Maintenance dispatch/writer wakeups are coalesced; WebSocket ping scheduling follows completion of the preceding ping. | Cancellation releases scheduled entries. Number of live connection/stream timers scales with admitted connections and streams; connection count remains unlimited by default. |
| Rate-limit history — `RateLimiterImpl` | Accepted requests add expiry entries per bucket. A fixed bucket policy limits entries by its allowance; bucket cardinality has no global cap. | Recording prunes the selected bucket and `currentBuckets()` prunes its snapshot. One coalesced server task now sweeps all limiters approximately once per second on the internal executor, releasing the decision lock between buckets and every 1,024 expired entries. Idle history is reclaimed without a diagnostic query. Cleanup stops between batches during server shutdown; a busy worker may delay it. Live bucket cardinality remains uncapped and the map can retain peak table capacity. |
| Application/provider state | Response headers, serialized objects, registered listeners, caches and user buffers have application-controlled size. | Request/body limits do not bound these objects. Application code can keep requests, sessions and payloads reachable after Mu finishes them. |

## What this means for a 64 MiB total limit

No 64 MiB claim can be made from these defaults. Even one request may aggregate a 24 MiB input plus intermediate and decoded objects. The JVM also needs class metadata, compiled code, thread stacks, GC structures and native/TLS allocations. Heap sizing alone cannot bound total process or container memory; kernel socket accounting also depends on which limit is being measured.

Until measured on an otherwise quiet machine, use streaming, modest request/message limits, explicit connection admission in Mu and/or at the deployment boundary, and at most one outstanding async send per producer. These practices reduce avoidable growth; they are not a tested 64 MiB configuration. A future memory-envelope campaign must distinguish process RSS from container-accounted memory, include idle and active TLS/H2/WebSocket connections, and observe recovery after cancellation and disconnect.

## Follow-up priorities

1. Decide the policy for excessive live rate-limit bucket cardinality. Expired-history cleanup is implemented; it is not a cap on live history or a guarantee of a particular total-memory envelope.
2. Consider optional pending-output byte/count limits for applications that cannot apply producer backpressure. Specify rejection, callback delivery and cancellation ownership first; include WebSocket sends and SSE. Connection admission is now available, with an unlimited default; choosing a safe default or a 64 MiB configuration still requires measurement.
3. Bound or coalesce HTTP/2 coordinator commands without blocking the reader behind a flow-controlled writer. Preserve control-frame progress, reset ordering and shutdown completion.
4. Measure a selected configuration's total-memory envelope and sustained recovery when the host is available. This audit does not establish Mu3/Mu4 performance parity or release acceptance.

## Verification

`AsyncResponseOutputTest` checks success, failure, cancellation and rejected writes for retained Mu-owned references, including delayed callback dispatch. Its object graph inspection follows Mu fields and actual collections; it does not depend on garbage-collection timing or open JDK internals. Existing cases verify ordering, exactly-once delivery, and buffer ownership until I/O acknowledges abort.

`AsyncOutputBufferTest` checks empty, small and multi-chunk array/direct/read-only buffers, slice offsets, exact bytes, bounded scratch-array size and a single flush. `AsyncOutputIntegrationTest` sends multi-chunk payloads over HTTP/1 and HTTP/2 with one application worker, plus cancellation of flow-controlled output. Existing `LifecycleRecoveryTest` covers slow-peer disconnect, timeout and shutdown retirement. These are small correctness tests, not performance or capacity tests.

Rate-limit cleanup is covered by `RateLimiterCleanupTest`: fake-clock expiry without a further request/query, signed nano-time wraparound, preservation of live and concurrently renewed buckets, other-request progress between bounded batches, one coalesced task for multiple limiters, executor rejection recovery, no timer for an unconfigured server, and shutdown of queued/running cleanup. Existing `RateLimiterTest` covers atomic decisions and HTTP/1/HTTP/2 behavior.

## Configuring connection admission

Set `withMaxConnections(n)` on the server builder to bound admitted connections across every HTTP and HTTPS listener. Zero is the unlimited default; negative values are rejected. Choose `n` from the deployment budget and workload, separately from `withMaxConcurrentRequests(n)`. An HTTP/2 connection uses one connection slot even with multiple active streams. A WebSocket keeps its slot after the upgrade request finishes. Setup sockets count before PROXY or TLS negotiation, including time spent waiting for an internal worker.

`withListenBacklog(n)` separately sets the requested OS queue length on each HTTP/HTTPS listening socket. The default remains 50; values must be positive. The getter reports the requested value, not a measured queue capacity. [Java documents the effective backlog as implementation-dependent](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/net/ServerSocket.html): it may be capped or ignored. This is a queue of connections waiting for acceptance, not the count already admitted by Mu and not a socket receive/send buffer size.

At capacity, the acceptor waits on a condition without holding a lock across socket I/O. Waiting before `accept()` does not reserve capacity: an idle HTTPS port cannot take the last slot away from HTTP. A shared atomic admission decision after acceptance closes any excess candidate before setup when listeners race. Overload may therefore produce connection delay, refusal/reset or timeout, rather than HTTP 503. `rejectedDueToOverload()` counts candidates actually rejected by Mu, not clients waiting in the OS backlog. Admission is released after socket closure and cleanup; timed-out setup and late worker retirement cannot release the same slot twice. This bounds admitted sockets, not all application tasks or total memory.

`ConnectionAdmissionTest` verifies concurrent last-slot admission, non-reserving waits, idempotent retirement, interruption and listener/server stop signals. `ConnectionLimitTest` checks idle HTTP/HTTPS reuse, silent TLS setup, shared ports, simultaneous HTTP/2 streams, WS/WSS upgrades, idle and PROXY setup timeouts, disconnect and shutdown. `ConnectionRejectionTest` checks internal executor rejection and recovery with both unlimited and capped admission. These bounded checks make no performance or capacity claim.
